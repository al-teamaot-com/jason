# Bounded Owner objective approval policy v1

Status: proposed adoption through an exact governed installation. This document
has no production effect merely because it is committed or merged.

## Adoption boundary

An independently authenticated Owner may adopt this version for explicitly
registered objective handlers in the exact installation scope. Record this
document's SHA-256, effective handler/profile hashes, Owner identity, exact
activation candidate and rollback in the Root installation receipt. Existing
unmigrated approval and release interfaces retain their effective requirements.

## One original decision

The Owner reviews one immutable plan: tenant, requester and approver role,
ordered capabilities, exact target artifacts, production effects, disruption
ceiling, exclusions, policy digest, expiry and covered recovery/rollback.
An authenticated Approve creates one original decision, never standing Root
authority. A Deny authorizes no production effect. Existing independently
required financial, disruptive-action and core-change approvals are preserved.

Root seals privileged material before delivery and sends its own exact review
through the existing bot. Bind the signed callback to the real provider message,
issued-card challenge, registered gateway, active licensed Owner identity and
current explicit grants. Reject unverified chat assertions, caller-supplied
approval flags, synthetic provider IDs and transformed legacy signatures.

## Continuation

Derive unique per-step execution claims from that original plan and decision.
Before each step independently verify current authority, policy, expiry and
revocation, immutable scope/artifact, source/CI, freeze/health, risk gates and
prior-step readback. Routine execution, diagnosis, tests, verification and
covered recovery do not ask for another Owner response.

Current v1 documentation registration permits exactly restore then scheduled
verification, with a fixed artifact source and exact rollback. It allows only
the two mechanically generated documentation state files to change as its own
publication effect, using the existing generated branch/PR and control-board\nissue #526. Later requests for this registered template use the same local\nworkload issuer and one new original decision per objective; no Root setup or\nper-step vote is required. Repeat jobs require fresh invocation evidence and\npreserve earlier acceptance records. It does not permit arbitrary source changes, business provider
writes, a changed tenant/component, wider disruption or a general Root shell.

A materially changed remaining objective, expired/revoked grant or genuinely
new independent approval boundary requires one revised full-plan decision.
Never reinterpret an old consumed exact-action approval as this new policy.

## Outcomes and recovery

Decision recorded, running, blocked, unknown and verified complete are distinct.
Retain immutable human evidence, canonical claims and native outcomes. Recover
completed effects through independent readback under the same original grant.
Never reset a consumed claim, forge success or blindly repeat an unknown effect.
Rollback preserves all newer decisions and evidence. Completion needs live
operational acceptance, not just code, green CI, installation or a card send.

## Retained callback handoff (source review, 2026-11-27)

A failure between independently verified Root admission and canonical
approval acceptance is distinct from an explicit denial. The existing
universal plan database retains the exact signed callback as non-bearer
transport evidence and an immutable evidence-hash scheduling pointer.
The existing maintenance worker may reconcile an atomically accepted
canonical decision or retry the exact callback while the original signed
transport is still fresh. Every retry uses the unchanged Root verifier,
current policy and approver binding, and canonical approval service.
A denial, changed evidence, revoked authority, or expired unaccepted
callback terminates the handoff; none can create a grant. Do not backdate
verification or infer a decision from a retained scheduling record.
Native step claims, independent readback, and release gates remain
unchanged. No additional approval issuer, signer, scheduler, or authority
store is introduced. The transport's original lifetime is not extended.

This source change is limited to the already registered Owner-objective
Teams workflow. It does not register the rollback-retention action,
enable a ChatGPT maintenance approval transport, or authorize production
installation. The failed terminal retention confirmation is not a
recoverable authenticated decision under this policy. Deployment and
any future action registration remain subject to independent governed
review and exact authorization. Source review is not live acceptance.
