# Jason Dual-Drive Storage Autorepair — Owner directive (2026-10-25)

## Scope

Jason should maintain disk capacity without recurring Owner intervention when one of its two independently mounted filesystems has safe headroom. The production root `/` and second archive filesystem `/srv/jason/archive` are monitored by the **existing five-minute self-heal watchdog** using allocatable, reserved-block-aware usage and inode checks. Start safe maintenance at **80% occupancy**. When **both** are 80% or higher, issue a deduplicated Teams Owner capacity escalation; never hide either filesystem's actual condition. A missing/unhealthy archive, failed capacity proof, or repairs requiring disruptive actions also merits a bounded exception escalation.

## Current standing-safe automated operation

Two narrowly reviewed operations are available: `scoped_unused_buildx_cache_cleanup` in the production watchdog and `archive_reconstructible_clean_detached_worktree` **only in a separate governed engineering invocation**, under `config/operations/host-storage-autorepair-v1.json`. It is implemented separately from the read-only detector in `tools/jason_storage_autorepair.py` and called from the **existing** watchdog in an isolated, bounded step. No new timer, root access, persistent worker, image prune, log truncate, service restart, or provider write is introduced. The automatic cache operation uses only `docker buildx prune --builder default --filter until=24h --force` to evict stale **unused build cache**, not Docker images or volumes; it checks for running build jobs and independently verifies reclaimed allocatable root bytes. Cache can be rebuilt. A nonzero exit status is fail-closed.

A separate engineering archival invocation (not the production watchdog) requires: independent archive mount/device; root at/above 80% and archive below 80%; destination at least 20 GiB allocatable free and projected below 80%; archive inode reserve; a registered worktree under the exact allowlisted source path at least 21 days old; detached and unlocked; all tracked/untracked/ignored files clean; HEAD an ancestor of protected `origin/main`; no currently discoverable process references. Never act on active branches or modified worktrees. Archive at most ten worktrees, 128 MiB each and 512 MiB total in a cycle. Use an exclusive lock, private 0600 tar and manifest on the archive drive, verify tar structure and SHA256, **then** ask Git to retire the checkout without `--force`. A failed check or copy retains the source unchanged. Never auto-delete archived tar/manifest. Rerun the original independent capacity detector and record the readback. The owner escalation is suppressed for that storage incident only while the production watchdog made independently verified build-cache cleanup progress. Cold archival remains outside the protected watchdog sandbox until the engineering maintenance lane is separately wired and released.

The Owner's new authorization **does not** grant blanket rights over active SQLite/WAL databases, OpenBao security audit files, active worktrees, Docker volumes/images (including immutable release and rollback images), production backups, releases, approval records, or user-disruptive operations. Host mount identity, root-control, CCC and production release gates remain mandatory. The dry-run is `PYTHONPATH=tools python3 tools/jason_storage_autorepair.py --dry-run`. Full automated behavior is enabled only after an exact-SHA governed deployment; source merge is not production acceptance.

## Known separate capacity drivers

On October 25 the primary drive was about 96% used with the secondary archive only 5% used. The active OpenBao audit log and live orchestration-events SQLite database each occupied about 21 GiB, plus about 25 GiB of development worktrees. Do **not** remove, truncate, or move these live security or operational artifacts as ordinary junk. OpenBao documents audit-file rotation by moving/renaming the audit file and signalling `SIGHUP` so its file device reopens; because a reload can be user-disruptive, that action needs specific technician approval and a tested audited continuity plan before it is enabled. Review event-DB retention/archiving separately with an atomic SQLite-aware migration, audit preservation, rollback and space validation. If automatic cache maintenance cannot restore adequate capacity, identify and escalate the precise remaining guarded maintenance blocker via Teams rather than claiming the drive is fixed. Archive support is not yet wired into the unattended engineering lane.
