# Approved Workflow Client Communication

## Section Goal

Allow Jason to send approved canned or strictly source-parameterized client-facing messages for **all approved communication classes**, not only client questions, when the operational workflow, message class, exact template and target audience have each been authorized.

## Trigger

A ticket, onboarding, documentation assurance, VulScan/security, or other approved workflow submits a request bound to a real Autotask ticket, declares `service.ticket.client.notification.create` as an allowed capability, and selects an exact source-controlled template ID. All workflow types use this same outbound process.

## Scope

This is the **one** outbound communication process for all client-facing Jason workflows. Every outbound message requires a real, correctly associated Autotask ticket before any send. The governed process applies to client-facing ticket communications generated by ticket, onboarding, documentation, security, and other approved workflows: status/progress notices, completion or resolution verification, coordination, client questions, low-risk instructions, and restricted security/approval/business notices. The 120-question catalog is only one content source. See `docs/operations/AOT-External-Client-Message-Classes.md` for message classification and authority. This does not authorize free-form client messaging or artificial TimeEntries.

## Identification

Each message is identified by the exact pair:

- `workflow_id`
- `template_id`

The pair must resolve uniquely in `config/client_communications/approved.json`. Every request must also identify and verify the exact Autotask `ticketID`, its authoritative `companyID`, and its ticket contact; missing ticket identity is an immediate deny. The ticket is the audit/follow-up anchor even when the underlying task began in onboarding or documentation.

## Expected State

The selected workflow has a durable owner promotion, the client-notification capability is included in that promotion, the template is enabled in source control, and the Autotask ticket has an authoritative client contact.

## Persisted States

The workflow keeps its normal durable work state. Client-message deduplication uses a fingerprint derived from the workflow ID, template ID, title, body, recipient policy, and notification requirement.

## Diagnostics

Before sending, Jason validates the exact ticket ID and authoritatively reads the existing ticket, ticket company opt-in UDF (once the separately approved opt-in profile is activated), and ticket contact. Ticket company and contact company must match. The recipient is derived from the ticket contact; arbitrary recipient substitution is not allowed.

## Decision Gates

A client message may be sent only when all of the following are true:

1. A real Autotask ticket already exists, is verified by governed read, belongs to the intended client, and is bound to the originating workflow. If none exists, a separate governed ticket-create step must be completed and verified **before** this process may send. No off-ticket message, unverified ticket, or silently created duplicate is allowed.
2. The workflow has an exact durable owner promotion.
3. `service.ticket.client.notification.create` is allowed by that promotion.
4. The exact workflow/template pair is enabled in the approved-message registry.
5. The ticket and contact belong to the same Autotask company.
6. The contact has a valid email address.
7. When required by the template, the contact is enabled for email notifications.
8. When the separately approved Company-UDF opt-in profile is active, `enable_jason_outbound_comm` must be explicitly True on the exact ticket company; missing/null/False or ambiguous denies sending.
9. The message class, evidence and data-release policy must authorize the exact content; restricted or sensitive classes continue to require their independent human decision.

## Remediation

The connector reconstructs the approved title and body from source control and fixes visibility metadata server-side. Existing fixed non-question notices (including VulScan) are supported; the current client-question catalog supports one bounded ticket reference. Future generic semi-canned slots require separate source-backed rendering and per-field verification, not unconstrained LLM-generated text.

## Retry and Recheck Rules

Client-notification creation is non-idempotent. The workflow must use its durable template fingerprint to avoid duplicate sends. Failed or unverified writes fail closed; no blind retry is permitted. Verified sends, delivery state, expected replies and required escalation are tracked against the same ticket.

## Activation

Production activation requires:

`JASON_AUTOTASK_CLIENT_NOTIFICATION_PROFILE=approved-workflow-client-notification-v1`

The capability remains fail-closed when this profile is not enabled.

## Dependencies

- Owner-approved playbook autonomy
- Autotask governed mutation execution
- Approved client-message registry
- Existing or separately governed-created, client-bound Autotask ticket with verified readback
- Authoritative Autotask ticket/contact reads
- Ticket-note post-write readback
- Notification-history verification when required by the workflow

## Documentation

Adding or changing an autonomous client message requires a source-controlled registry change and normal repository review/validation.

## Failure and Escalation Handling

Missing approval, unknown templates, workflow/template mismatch, cross-company contact mismatch, recipient override, disabled email notifications, provider write failure, or failed readback must stop the client communication.

## Verification

The Autotask TicketNote create operation retains mandatory post-write readback. Workflows that require proof of outbound notification must also verify the notification in Autotask Notification History.

## Completion

A client-communication step is complete only after the governed write and required verification succeed.

## Required Capabilities

- `service.ticket.client.notification.create`
- Read capabilities needed to resolve the ticket/contact and any workflow-specific notification history

## Section Goal Closure

Jason can send approved non-question notices **and** approved questions through one governed workflow/template-based transport, without general free-form client communication authority. Generic variable insertion, class-specific promotion, Company UDF activation and TimeEntry visibility require their own acceptance evidence.
