# Owner signer recovery — P0 source and independent root acceptance

**Scope:** Governed one-shot restore of exactly one read-only Ed25519 signer mount on the existing `jason-mcp-pilot`, with **no code or image release**. This is the reusable policy-pinned recovery pattern for incident #2450; this concrete policy is valid **only** for production LKG `690250b4d21f32cce79cab9f5b4c18cf93e7e94a`. A different baseline requires a separately reviewed exact policy and root installation, never a caller-provided arbitrary SHA.

**State as of source review:** Implementation and synthetic tests only; **not installed as a root recovery capability**, not authenticated or run against production, and not a bypass around the production freeze, breaker, provider or release authority. Existing ticket-processing baseline is preserved; its independently reported backlog remains a separate problem.

## Exact boundaries and trust

1. The `--execute` entrypoint refuses non-root users and refuses execution from a user-writable Git worktree; it requires `/usr/local/lib/jason/owner_signer_recovery.py`, securely installed root-owned/nonwritable, and an exact root-owned JSON profile at `/etc/jason-owner-release/owner-signer-recovery-policy.json`.
2. The root profile pins a single action, existing LKG source/image IDs, original freeze SHA-256, existing host signer public-key SHA-256, original native deployer path and **the SHA-256 fingerprints of both reviewed source and deployer**. A root-private `/etc/jason-owner-release/owner-signer-recovery-ledger` (0700) refuses one-shot replays; an exclusive root-owned 0600 claim is fsynced **before** any container change and a separate outcome receipt records success or rollback.
3. The preflight independently checks root-owned control and drift files, **closed breaker**, complete matching protected LKG, latest clean drift (within 180 seconds), runtime healthy, MCP running, exact Docker image IDs, exact runtime/MCP revision labels, exact host symlink, unmodified freeze bytes, no existing signer bind, and pinned local private/public Ed25519 matching (without printing or exporting secret bytes).
4. On exact action request, the process generates a **fresh Microsoft Entra device code** for the existing MCP application and prints the code and official sign-in URL only. It validates the resulting JWT using Microsoft JWKS, RS256, exact AOT tenant/issuer/audience, expiry/not-before/issued-at, `Jason.Read` scope, and the two already-authorized Owner Entra object IDs. It never accepts self-declared Owner identity, a ChatGPT typed approval, local JSON approval or a previously issued release signature. The access token stays in memory and is never written to a file or logged.
5. After repeat preflight, only the existing native `tools/deploy_live_container.py` may replace **the same MCP source/image**, adding exactly the existing host `0400` signing key as a read-only bind and setting `JASON_OWNER_RELEASE_ED25519_KEY_PATH` to its mounted path. The script does not activate import profiles, modify runtime, write contacts, change root policy, touch tickets, remove the freeze, or restart other services. MCP replacement is a service interruption permitted only by the specific authenticated Owner recovery.
6. Postflight validates new MCP identity with unchanged image, nonprivileged sandbox, same preexisting mounts/environment/network/user, exactly one added readonly signer mount, matching public-key fingerprint read by the MCP service, runtime container unchanged, host and freeze unchanged, root LKG and breaker still clean, plus native healthz acceptance. On failure, the existing native deployment logic rolls back or the wrapper restores the exact saved prior MCP container. A failed attempt cannot silently retry without a new approved root profile.
7. A *subsequent* new authenticated ChatGPT Owner decision is required for the unrelated full Constant Contact release `release-a58edab657fa0af5`, SHA `a58edab657fa0af506535b7a7de6a124e1a07f64`, exact reviewed scope SHA-256 `9b80ea96b10e478ec69f195ce0fddc76a6abf73b95f8847b0fedb97b4835b9cf`. The prior signed approval is for a failed different release and cannot be reused. The native Release Manager, protected freeze, CCC, root health and rollback gates remain required.
