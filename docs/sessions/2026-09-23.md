## 5. Provider identity binding observation — ARCHITECTURAL AMBIGUITY

The original action fingerprint bound:

- principal;
- organization;
- client;
- canonical capability; and
- canonical arguments.

It did **not** explicitly bind the selected provider identity. This exposed an architectural ambiguity: provider mutation authorization must bind the provider selected for the mutation while still allowing playbooks to inspect different devices or evidence sources inside an already-authorized client scope.

**Design principle:** provider substitution and resource/device flexibility are different concepts. Provider mutation authorization must not permit silent provider substitution merely because the canonical action text is unchanged.

## 7. Execution-plan binding remediation — ISOLATED IMPLEMENTATION PASS

The architectural remediation introduces two independent bindings.

### Intent fingerprint

Binds the semantic Jason action approved by governance.

### Execution-plan fingerprint

Binds the concrete provider mutation after provider selection, symbolic resolution, normalization, and defaulting are complete.

The governed execution sequence is now designed as:

1. approve intent;
2. resolve provider;
3. prepare concrete execution plan;
4. bind and consume the approval to that plan;
5. independently re-prepare the execution plan immediately before provider invocation;
6. compare the concrete plan fingerprint;
7. invoke only when the second concrete plan still matches the authorized plan.

The execution-plan fingerprint binds, where applicable:

- `principal_id`;
- `organization_id`;
- `client_id`;
- canonical capability;
- selected provider ID;
- provider capability / operation;
- method/action;
- resource type;
- resource identifier / target;
- normalized provider-relative path;
- normalized final provider payload;
- material query/operation parameters; and
- symbolic-resolution evidence.

The execution-plan security boundary deliberately excludes:

- secrets;
- authentication/authorization headers;
- correlation IDs;
- dynamically discovered provider hostnames; and
- other transport-only volatile information that is not intentionally part of authority.

If independent re-preparation changes provider, target, provider operation, symbolic mapping, normalized payload, or other material plan content, Jason fails closed with `EXECUTION_PLAN_MISMATCH` and performs zero provider writes.

## 12. Shared deadline and governed indeterminate recovery — SOURCE REMEDIATION COMPLETE

Shared security-framework remediation was completed at code/test checkpoint `bf072af` (`Harden governed recovery and shared execution deadlines`).

### Shared provider deadline

The prior connector boundary applied a fresh provider timeout separately to first plan preparation, independent re-preparation, and invocation. That could allow one logical approved action to consume multiple full provider time budgets. The remediation introduces one shared absolute provider-action deadline derived from the resolved provider `maximum_execution_seconds`. The same absolute deadline now spans both preparations and invocation, and nested connector deadlines may only tighten it; they cannot reset or extend it. Teams direct-invoker HTTP timeout also participates in the shared deadline.

### Continuation/recovery execution-plan binding

The original dual-plan implementation keyed its durable MCP path on `approval_id`. Continuation-based approvals use a separate durable continuation guard and recovery retries use a separate durable recovery guard, so they may legitimately reach Central Orchestrator without an MCP governed-execution `approval_id`. Central Orchestrator now treats every externally guarded approved EXECUTE continuation as plan-bound: first preparation records the concrete plan fingerprint, independent re-preparation must match exactly, and only the second prepared object may reach the provider. A mismatch records `provider_invoked=false` and stops. This preserves separation of replay responsibility while eliminating a legacy invocation fallback.

### Recovery retry implementation

`implementation/orchestrator/approval_recovery_retry.py` had been only a source stub while tests described the intended behavior. It now implements:

- in-memory and SQLite durable one-time recovery retry guards;
- exact recovery ID, organization, request, correlation, capability, and fresh-authority matching;
- `retry_authorized` disposition enforcement;
- claim-before-orchestration semantics so crash/failure never silently releases retry authority;
- Central Orchestrator-only execution; and
- approval audit evidence carrying the recovery ID and result.

Stale continuation/recovery tests were updated to current `OrchestrationRequest`, execution-policy, audit-recorder, and continuation-guard contracts rather than weakening production dataclass requirements.

### Operator procedure

A new provider-neutral runbook is recorded at `docs/operations/Governed-Mutation-Indeterminate-Recovery.md`. It requires read-only provider reconciliation, immutable disposition, no deletion/reset of consumed claims, fresh JKD-001 authority for retry, one-time recovery consumption, dual plan verification, normal provider readback, and a new recovery decision if the retry is also indeterminate.
