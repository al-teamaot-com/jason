## 3. Approval replay / idempotency vulnerability — CONFIRMED DEFECT, THEN FIXED

This was a confirmed security defect. Immutable approval evidence alone was insufficient because each replay could be presented as a newly generated execution/idempotency identity.

### Source remediation

The governed-execution path was changed so the approval is bound to one canonical action identity, can be consumed only once, and successful exact retries return the persisted result instead of invoking the provider again. The durable ledger records approval, fingerprint, idempotency, execution/correlation identity, consumption state, completion state, and replay/deduplication evidence.

## 5. Provider identity binding observation — ARCHITECTURAL AMBIGUITY

The original action fingerprint bound:

- principal;
- organization;
- client;
- canonical capability; and
- canonical arguments.

It did **not** explicitly bind the selected provider identity. This exposed an architectural ambiguity: provider mutation authorization must bind the provider selected for the mutation while still allowing playbooks to inspect different devices or evidence sources inside an already-authorized client scope.

**Design principle:** provider substitution and resource/device flexibility are different concepts. Provider mutation authorization must not permit silent provider substitution merely because the canonical action text is unchanged.

## 6. Post-approval normalization — ARCHITECTURAL GAP CONFIRMED

A zero-provider-write test proved that an identical approved canonical Autotask action could resolve to different concrete provider payloads when provider metadata changed after approval.

Approved semantic intent:

- `status = "In Progress"`
- `queueID = "Jason"`

Two concrete resolutions demonstrated the problem:

- Variant A: `status = 8`, `queueID = 29690001`
- Variant B: `status = 77`, `queueID = 39999999`

The original approval fingerprint remained unchanged even though the final provider mutation changed materially.

**Result before remediation:** ARCHITECTURAL GAP.

This finding is independent of the approval-replay defect. Replay protection can prevent a second use of an approval while still allowing the first approved action to drift during post-approval normalization unless the concrete provider mutation is also bound.

## 7. Execution-plan binding remediation — ISOLATED IMPLEMENTATION PASS

The architectural remediation introduces two independent bindings.

### Intent fingerprint

Binds the semantic Jason action approved by governance.

### Execution-plan fingerprint

Binds the concrete provider mutation after provider selection, symbolic resolution, normalization, and defaulting are complete.

The governed execution sequence is now designed as:

1. approve intent;
2. resolve provider;
3. prepare concrete execution plan;
4. bind and consume the approval to that plan;
5. independently re-prepare the execution plan immediately before provider invocation;
6. compare the concrete plan fingerprint;
7. invoke only when the second concrete plan still matches the authorized plan.

The execution-plan fingerprint binds, where applicable:

- `principal_id`;
- `organization_id`;
- `client_id`;
- canonical capability;
- selected provider ID;
- provider capability / operation;
- method/action;
- resource type;
- resource identifier / target;
- normalized provider-relative path;
- normalized final provider payload;
- material query/operation parameters; and
- symbolic-resolution evidence.

The execution-plan security boundary deliberately excludes:

- secrets;
- authentication/authorization headers;
- correlation IDs;
- dynamically discovered provider hostnames; and
- other transport-only volatile information that is not intentionally part of authority.

If independent re-preparation changes provider, target, provider operation, symbolic mapping, normalized payload, or other material plan content, Jason fails closed with `EXECUTION_PLAN_MISMATCH` and performs zero provider writes.
