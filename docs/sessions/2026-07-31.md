# Project Jason Session Record — 2026-07-31

## Session scope

This session focused on completing and governing the OpenBao Production Foundation, aligning the verified runtime deployment with source control, addressing documentation-build failures, and preserving architectural decisions in canonical repository artifacts.

## Important discussion

The session reviewed:

- OpenBao initialization, unsealing, audit logging, policy design, user authentication, AppRole authentication, and backup operation.
- The distinction between runtime state and source-controlled desired state.
- The connector as the credential-brokering and external-execution boundary.
- Separation between the authority chain and secret chain.
- The requirement that the orchestrator authorize work without possessing connector credentials.
- The role of the Secrets Broker and OpenBao in future connector authentication.
- The need for business-justified secret retrieval and future ephemeral credentials.
- The conflict between the existing MkDocs configuration and Jason's canonical numbered repository hierarchy.
- The requirement to classify repository artifacts and verify their canonical location before creation.
- The need to limit architectural expansion that does not unblock the next useful capability.

## Decisions made

1. OpenBao remains the approved secrets authority and storage platform for Project Jason.
2. Manual Shamir custody remains in place; cloud KMS auto-unseal is deferred.
3. The OpenBao backup service runs daily at 02:30 local server time.
4. Backup access uses a least-privilege AppRole and short-lived service token.
5. The connector is the controlled boundary that intersects:
   - the authority chain; and
   - the secret chain.
6. The orchestrator authorizes named operations but must not retrieve, possess, transmit, log, or expose connector credentials.
7. Connectors will retrieve only their assigned credentials through the governed Secrets Broker.
8. Secrets are retrieved because an approved business capability requires them, not merely because software requests them.
9. The numbered top-level repository hierarchy remains Jason's canonical knowledge hierarchy.
10. Documentation tooling must adapt to the canonical hierarchy rather than force canonical documents to move.
11. Generated artifacts are disposable and non-authoritative.
12. Repository architecture governs document placement.
13. Before creating a repository artifact:
    - classify the artifact;
    - verify its canonical location;
    - stop and seek a governance decision if no location is defined.
14. The Autotask read-only credential will not be stored until the surrounding Secrets Broker and connector governance are ready.
15. The next useful capability remains the Secrets Broker and first governed read-only connector after the current milestone is closed.
