# Jason Playbook: Idle Log Off Compliance

## 1. Section Goal

**Goal:**  
Detect, diagnose, repair, and verify Windows workstation Idle Log Off compliance when DRMM reports that the required Idle Log Off configuration is noncompliant.

**Success means:**
- Jason proves the exact device is in scope and should have Idle Log Off.
- Jason moves the ticket to queue **Jason** and sets **In Progress** before ticket-specific diagnostics.
- Jason distinguishes missing configuration from failed/partial configuration and from a bad remediation payload.
- When authorized and safe, Jason installs or repairs Idle Log Off using the approved AOT component.
- Jason verifies the device returns to compliant state and the DRMM alert clears.
- All diagnostics, remediation, job IDs, output, and verification are documented.

Do not consider the Section Goal complete until the controlled acceptance test succeeds and the remediation component/variables are approved for the intended autonomous scope.

---

## 2. Trigger

This playbook applies when either of the following is present:

- Autotask ticket title contains:
  `[Get Idle Log Off Status AOT Ver 08202024] - Compliant: False`
- DRMM alert is generated by:
  `Get Idle Log Off Status AOT Ver 08202024`
- DRMM policy:
  `AOT - Policy Idle Log Off Monitor/Resolve (Create Ticket)`

Known current monitor component:

- Name: `Get Idle Log Off Status AOT Ver 08202024`
- UID: `2b5de042-a3ec-4721-ba66-e0ca193a3604`
- Healthy monitor state: `Compliant=True`

Jason must confirm the trigger matches before starting.

---

## 3. Scope and Boundaries

### In Scope

- Windows workstations and laptops managed by AOT.
- Devices receiving the AOT Idle Log Off monitoring policy.
- Read-only validation of device identity, operating system, alert state, response history, and compliance state.
- Repair/install of the Idle Log Off configuration when:
  - the endpoint is confirmed in scope;
  - no documented exception exists;
  - the device is online;
  - approved remediation variables are available;
  - the exact remediation component is approved for the intended execution scope.
- Verification and ticket completion after authoritative healthy-state evidence.

### Out of Scope

- Windows Server unless explicitly documented as requiring this workstation control.
- RDS/session hosts, kiosks, shared-purpose devices, or other documented exceptions unless explicitly approved.
- Immediate forced logoff of a currently active user as part of troubleshooting.
- Arbitrary registry/task/file changes outside the approved component.
- Guessing component variables.
- Retrying a known-bad payload unchanged.
- Disabling the monitor to suppress the alert.
- Direct provider bypass.

Preserve:
- `direct_provider_access=false`
- Central Orchestrator authority
- exact requester grants
- provider/client isolation
- audit trail
- existing approval and disruption rules

---

## 4. Initial Identification

Before troubleshooting:

1. Identify the exact Autotask ticket and DRMM alert.
2. Identify client/site and endpoint.
3. Run the global device-association gate:
   - preserve an existing CI when correct;
   - if missing, resolve exactly one same-company active Autotask CI using authoritative DRMM UID evidence and associate it before substantive diagnostics;
   - if association fails due governance, set `state=identification_blocked`, document the blocker, and stop.
4. Confirm the endpoint is Windows workstation/laptop unless a documented exception says otherwise.
5. Confirm the alert originated from the Idle Log Off policy.
6. Confirm there is no documented device/site exception.
7. Confirm endpoint is online before claiming.
8. Immediately before first ticket-specific diagnostic:
   - move ticket to queue **Jason**;
   - set status **In Progress**;
   - set Work Type **Remote Support**;
   - require readback.

If identity or applicability is uncertain:

`state = identification_blocked`

---

## 5. Expected State

A healthy in-scope endpoint should show:

- Idle Log Off monitoring policy assigned.
- `Get Idle Log Off Status AOT Ver 08202024` reports `Compliant=True`.
- The required Idle Log Off mechanism is installed/configured using the approved AOT standard.
- No current Idle Log Off compliance alert remains open.
- No component error is present in the most recent remediation attempt.
- Configuration values match the approved AOT standard for that policy/site.

Current component descriptions indicate the AOT standard is intended to log off an idle workstation session after approximately four hours, but Jason must use the approved component/policy variables rather than infer or invent numeric values.

---

## 6. State Model

Persist one of:

`identified -> waiting_endpoint -> diagnosing -> compliant_stale_alert -> complete`

`diagnosing -> not_applicable -> documented_exception -> complete`

`diagnosing -> configuration_missing -> remediating -> verifying -> complete`

`diagnosing -> configuration_broken -> remediating -> verifying -> complete`

`diagnosing -> remediation_parameter_error -> blocked`

`diagnosing -> remediation_failed -> retrying -> verifying`

`diagnosing -> dependency_missing -> blocked`

`diagnosing -> identification_blocked`

`diagnosing -> escalated`

Do not repeat completed remediation after a successful terminal job unless verification shows the endpoint is still noncompliant.

---

## 7. Diagnostic Workflow

### Step 1: Confirm Device Applicability

**Purpose:**  
Prove the endpoint should have Idle Log Off.

**Evidence source:**  
Autotask + DRMM.

**Reads:**
- ticket/CI read
- endpoint device read
- DRMM alert read

**Expected result:**
- Windows workstation/laptop
- alert came from the AOT Idle Log Off policy
- no documented exception

### Decision

If applicable:
-> continue.

If server/RDS/kiosk/exception:
-> `not_applicable`; document and resolve/suppress through policy administration outside this playbook.

---

### Step 2: Inspect Alert and Response History

**Purpose:**  
Determine whether the endpoint is simply noncompliant or whether automatic remediation already failed.

**Evidence source:**  
DRMM open alert + response actions + diagnostics.

**Expected result:**  
Alert shows `Compliant=False`; response history may show a remediation component attempt.

Known production example on AVMAC-1096:
- Ticket: `T20260924.0043`
- Alert UID: `9d34f135-8393-4e7f-b2a8-064a1e98eb07`
- Existing policy response invoked the older setter and failed with:
  `Invalid MyFileDestination`

### Decision

If no remediation was attempted:
-> continue to configuration diagnosis.

If remediation failed:
-> classify by failure type before retrying.

If the exact failure is parameter/input related:
-> `remediation_parameter_error`; do not blindly rerun the same payload.

---

### Step 3: Determine Missing vs Broken Configuration

**Purpose:**  
Decide whether Jason needs an install/configure action or a repair.

**Evidence source:**  
Monitor result, component output, job history, approved diagnostic evidence.

**Expected result:**  
One of:
- compliant;
- configuration absent;
- configuration present but nonfunctional/misconfigured;
- remediation payload invalid.

Jason must not treat `Compliant=False` alone as proof that the mechanism is absent.

---

### Step 4: Validate Remediation Component and Variables

**Preferred remediation component:**
- `Set Idle Log Off AOT Ver 02042026-1`
- UID: `acc6a240-881d-4655-9470-87f60c8e35e8`

**Legacy component:**
- `Set Idle Log Off AOT Ver 08202024`
- UID: `dec3eab8-52a1-4d5b-8c30-f7dab9ff63bf`

The legacy component is implicated in the AVMAC-1096 `Invalid MyFileDestination` failure and must not be blindly retried with the same payload.

Required variables exposed by the setter:
- `CheckForIdleEvery_X_Min`
- `MyIdleTimeInMin`
- `MyWarningTimeOut`
- `MyFileDestination`

**Rule:**  
Values must come from the approved AOT policy/component configuration or another authoritative documented standard. Jason must never invent them.

---

## 8. Decision Gates

Before remediation all must be true:

- exact endpoint and CI resolved;
- ticket moved to Jason / In Progress;
- endpoint online;
- Windows workstation/laptop or specifically approved exception;
- monitor/policy proves the control is required;
- no documented exclusion;
- current noncompliance confirmed;
- latest remediation history understood;
- exact preferred component resolved by live UID/name;
- approved variable values available;
- component execution authority allows the exact remediation.

If any gate fails:
-> `blocked` or `escalated`.

---

## 9. Remediation

### Remediation A: Install/Repair Idle Log Off

**Action/component:**  
`Set Idle Log Off AOT Ver 02042026-1`

**Preconditions:**
- all Section 8 gates pass;
- exact approved variables are supplied;
- no active conflicting job.

**Approval classification:**  
Modifying; policy-enforcing; potentially user-impacting at future idle timeout.

This action is eligible for autonomous use only after controlled acceptance and standing-safe approval for the exact component metadata/variables. The playbook itself does not grant authority.

**Verification required:**
- component job reaches terminal success;
- stdout/stderr reviewed;
- monitor subsequently reports `Compliant=True`;
- exact alert clears or is resolved after healthy-state readback.

### Legacy Setter

Do not use `Set Idle Log Off AOT Ver 08202024` automatically when the previous execution failed with `Invalid MyFileDestination`.

---

## 10. Retry Policy

- Maximum remediation attempts: `2`.
- Never retry the exact same payload after a deterministic parameter error.
- A second attempt is permitted only when new evidence changes the expected outcome, such as corrected approved variables or an updated component.
- Never dispatch a duplicate job while the prior job is active.

After two failed meaningful attempts:

`state = escalated`

---

## 11. Periodic Rechecks

After remediation:

- First recheck: approximately 15 minutes, matching the current monitor auto-resolve window.
- Second recheck, if needed: 30 minutes after the first.
- Re-read the exact alert and current compliance state.
- Poll the same remediation job until terminal; do not redispatch.

Stop when:
- compliant and alert cleared;
- endpoint goes offline;
- retry limit reached;
- dependency/authority blocker is reached.

---

## 12. Aging / Stale Condition

If endpoint stays offline:
- do not claim or remediate;
- recheck when it returns.

If the alert persists more than one business day after a verified successful remediation:
- inspect monitor logic and component/policy mismatch;
- do not keep reinstalling.

If repeated tickets recur after successful remediation:
- investigate policy variables, monitor logic, or configuration drift as a problem-management item.

---

## 13. Dependency Handling

Dependencies may include:
- authoritative variable set for the current AOT standard;
- component standing-safe approval;
- valid CI association;
- endpoint availability;
- corrected DRMM policy response configuration.

If a dependency is missing:
1. confirm it is truly missing;
2. search for an existing issue/support item;
3. avoid duplicates;
4. create/cross-reference one when authorized;
5. set `state=blocked`.

Do not borrow values from another client or guess `MyFileDestination`.

---

## 15. Failure Handling

Examples:

- `Invalid MyFileDestination`:
  - classify `remediation_parameter_error`;
  - do not retry unchanged;
  - validate the approved variable source / newer component.

- Component job failure:
  - collect stderr/stdout;
  - determine deterministic vs transient failure;
  - retry only within Section 10.

- Endpoint offline:
  - `waiting_endpoint`.

- CI association governance failure:
  - `identification_blocked`;
  - document and stop substantive endpoint work.

---

## 16. Escalation Criteria

Escalate when:
- exact endpoint/CI cannot be established;
- endpoint is not an applicable workstation and no explicit exception exists;
- approved remediation variables are unavailable;
- component is not authorized for execution;
- two meaningful remediation attempts fail;
- remediation would require a disruptive/manual action outside the approved component;
- monitor remains false after verified successful repair;
- recurring tickets indicate systemic policy drift.

---

## 17. Verification

Authoritative resolution requires:

1. endpoint online;
2. remediation job terminal success when remediation was required;
3. `Get Idle Log Off Status AOT Ver 08202024` returns `Compliant=True` or equivalent authoritative DRMM healthy evidence;
4. no current component error;
5. triggering alert is cleared/resolved;
6. ticket note records final state.

A successful setter job alone is not enough.

---

## 18. Completion Criteria

Ticket may complete only when:

1. exact object identified;
2. ticket moved to Jason before substantive work;
3. applicability confirmed;
4. diagnostics completed;
5. configuration repaired/installed if needed;
6. monitor is compliant;
7. alert cleared;
8. final note present.

If the endpoint is a documented exception, completion requires documentation of that exception and correction of the policy assignment outside this playbook.

---

## 19. Final Resolution Note

Include:
- original `Compliant=False` condition;
- whether control was missing, broken, or failed because of bad remediation parameters;
- component/job used;
- remediation attempts;
- final `Compliant=True` evidence;
- alert resolution status;
- verification timestamp.
