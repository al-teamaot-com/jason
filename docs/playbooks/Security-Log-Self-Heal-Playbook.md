# Jason Playbook — Windows Security Log Unreadable / Self-Heal

## 1. Section Goal

Jason must identify, document, remediate, verify, and close Windows Security Log unreadable conditions reported by Datto RMM, while preserving governance and autonomously cleaning up any expected EDR/SOC side-effect alerts or Autotask tickets generated by the approved repair when correlation is exact. Success requires healthy post-repair verification, exact original-alert resolution, exact side-effect correlation/cleanup, automatic ticket completion with readback, and no closure of unrelated security activity.

## 2. Trigger

Apply when Datto RMM reports the Windows Security event log is unreadable, including errors such as:

- `Could not retrieve information about the Security log. Error: The data is invalid.`
- Security Log monitor state `Unhealthy - Security log NOT readable`

## 3. Scope and Boundaries

In scope:

- Autotask ticket creation/read/update/note
- Datto RMM endpoint identity, online status, Security Log alert reads
- Governed Security Log Quick Test and Self-Heal components
- Post-repair verification
- Exact DRMM alert resolution
- Correlated EDR/SOC alert and ticket cleanup
- Automatic completion of the primary and exactly correlated process-generated Autotask tickets after healthy verification

Preserve Central Orchestrator authority, exact grants, provider/client isolation, approval requirements, audit trail, and `direct_provider_access=false`.

**Owner policy decision — 2026-09-28:** the target autonomous workflow is one bounded Security Log Self-Heal attempt followed by independent healthy verification, exact original-alert resolution, exact correlation/cleanup of expected repair-generated security side effects, and automatic Autotask completion. Human Review is required only when remediation fails, correlation is uncertain, unrelated security evidence appears, or another out-of-scope action is required. Production authority remains contingent on exact implementation/acceptance of the completion and cleanup branch.

## 4. Initial Identification

Identify and record:

- exact device hostname and Datto device UID
- site/client
- exact Security Log alert UID
- Autotask configuration item
- existing matching open ticket, if any
- endpoint online/offline state

If no appropriate ticket exists and ticket creation is authorized, create one and associate the configuration item.

## 5. Expected State

Healthy state requires:

- Windows Security event log is readable
- Security Log Quick Test returns `Status=Healthy`
- original Security Log DRMM alert is no longer open
- any expected Self-Heal-generated EDR/SOC alert is correlated, documented, and no longer open
- any correlated process-generated Autotask ticket is documented and completed

## 6. State Model

`identified -> waiting_offline -> diagnosing -> remediating -> verifying -> resolving_original_alert -> correlating_side_effects -> cleanup -> completing_ticket -> complete`

Alternate terminal state: `human_review`.

Persist ticket ID, device UID, original Security Log alert UID, Quick Test job UID, Self-Heal job UID, repair attempt count, repair start/completion timestamps, expected side-effect correlation window, correlated EDR/SOC alert IDs, correlated Autotask ticket IDs, cleanup results, and final ticket-completion readback.

## 7. Diagnostic Workflow

1. Confirm exact device and Security Log alert.
2. Read endpoint online state.
3. If online, run:
   - `Security Log Quick Test [WIN] AOT Ver 12012025-1`
   - component UID `a50d486b-2cce-4658-9e11-64fb6bf9ab9d`
4. Poll the exact job to terminal state.
5. Read exact StdOut.
6. Branch:
   - Healthy: skip Self-Heal and proceed to verification/alert cleanup.
   - Unhealthy with the known Security Log error: proceed to remediation gate.
   - Different failure: escalate.

## 8. Decision Gates

Before Self-Heal:

- exact device identity confirmed
- endpoint is online
- Quick Test confirms the known unhealthy Security Log condition
- exact Self-Heal component authority is valid for this playbook
- no Self-Heal has already been attempted for the same unchanged incident state
- SOC/SIEM side-effect behavior is covered by the approved playbook and correlation rules below

Operational notice:

> This Security Log repair clears/rebuilds the Windows Security event log and can legitimately generate a RocketCyber/EDR/SOC event-log-cleared alert. Jason may autonomously clean up only an exactly correlated expected side effect. Any ambiguous or additional security activity requires Human Review.

## 9. Remediation

Run:

- `Security Log Self-Heal [WIN] AOT Ver 11262025-2`
- component UID `cdd297b4-378f-4ffc-b272-56833e926c81`

Authority classification: modifying, security-sensitive.

Expected output includes:

- `Result=Repaired`
- Security channel registry values reset
- Security log cleared via `wevtutil cl Security`
- post-repair Security log health check passed

The component result alone is not sufficient for completion.

## 10. Retry Policy

Maximum autonomous Self-Heal attempts for the same unchanged incident state: **1**.

Do not redispatch an existing active job. Poll the same job and retrieve its output.

If the independent Quick Test remains unhealthy after the one Self-Heal attempt, stop and hand off to Help Desk I / Human Review. Do not automatically clear/rebuild the Security Log a second time.

## 11. Periodic Rechecks

If endpoint is offline:

- document offline state
- leave ticket open/pending
- recheck when the device reconnects
- do not run repair while offline
- suppress duplicate tickets and duplicate scheduled work

## 12. Aging / Stale Condition

If the endpoint remains offline for an abnormal period, investigate retirement, replacement, stale device objects, or broader connectivity/management issues rather than retrying indefinitely.

## 13. Dependency Handling

If configuration-item association, Datto component discovery, Autotask ticket creation, or alert resolution is unavailable:

1. confirm the missing dependency
2. document the blocker
3. avoid bypasses/direct provider access
4. create or update the appropriate Project Jason support/TODO item when required
5. resume from persisted state after the dependency is restored

## 14. Documentation Requirements

Use the standard technician-scannable Jason note layout wherever practical:

- **STATUS**
- **NEXT STEP** or **ACTION REQUIRED**
- **DEVICE / ALERT**
- **KEY EVIDENCE**
- **WHAT JASON DID**
- **SECURITY SIDE EFFECTS**
- **CHANGES MADE**
- **JASON STATE**

For a successful case, lead with:
- STATUS: VERIFIED RESOLVED
- NEXT STEP: Resolve exact correlated alerts and complete tickets automatically
- SECURITY LOG: Healthy / readable
- SELF-HEAL: Not required or completed successfully
- SECURITY SIDE EFFECTS: None, or exact expected event-log-cleared alert correlated to Jason repair

For Human Review, lead with:
- STATUS: HUMAN REVIEW REQUIRED
- ACTION REQUIRED: Review failed remediation or ambiguous/unexpected security evidence

Also document:
- device and original alert identity
- online/offline state
- Quick Test job ID/result
- Self-Heal job ID/result when used
- independent verification job ID/result
- exact DRMM original-alert resolution result
- any correlated EDR/SOC alert and Autotask ticket
- final cleanup and ticket-completion readback

Suggested note titles:

- `Jason - Security Log - Asset Validation`
- `Jason - Security Log - Diagnostic`
- `Jason - Security Log - Remediation`
- `Jason - Security Log - Verification`
- `Jason - Security Log - Process-Generated Ticket Cleanup`
- `Jason - Security Log - Resolution`

## 15. Failure Handling

Document failed reads, component-discovery failures, job failures, missing StdOut, alert-resolution readback races, provider errors, or contradictory evidence.

A readback race must be resolved by checking authoritative current alert state/history before declaring failure or success.

## 16. Escalation Criteria

Hand off to Help Desk I / Human Review when:

- endpoint identity is uncertain
- the one bounded Self-Heal attempt fails
- Quick Test remains unhealthy after that attempt
- a different Security Log error appears
- expected side-effect correlation is ambiguous
- additional/unexplained EDR/SOC activity appears in the correlation window
- exact original-alert or side-effect-alert resolution cannot be verified
- required provider capability is unavailable
- remediation would require a separate disruptive action

## 17. Verification

After Self-Heal, independently rerun:

- `Security Log Quick Test [WIN] AOT Ver 12012025-1`

Required healthy evidence:

- `Status=Healthy`
- `Security log is readable.`

Then resolve the exact original Security Log DRMM alert and verify it is no longer open.

If healthy verification succeeds, proceed automatically into the side-effect correlation/cleanup branch. Do not stop for routine Help Desk review.

## 18. Completion Criteria

Complete the primary remediation ticket automatically only after all of the following are true:

1. independent Quick Test is healthy
2. original Security Log alert is resolved/not open
3. Self-Heal evidence is documented
4. all expected process-generated EDR/SOC alerts have been correlated
5. all process-generated Autotask tickets created by the repair have been documented and completed or otherwise dispositioned
6. unrelated alerts/tickets remain untouched
7. final resolution note is present
8. primary Autotask completion write succeeds and status=Complete is independently read back

A routine healthy case, including one with an exactly correlated and cleaned-up expected SOC/EDR side effect, does **not** require Help Desk review.

### Mandatory Process-Generated Ticket Cleanup

The Security Log Self-Heal may trigger EDR/SOC detections such as:

- `(Defense Evasion-T1070.001) Windows Event Logs was cleared`

Jason may autonomously disposition an expected side-effect alert only when **all** correlation gates pass:

1. exact same endpoint/device identity as the Self-Heal target;
2. alert creation/event timestamp is after the Self-Heal began and within a bounded expected correlation window around the repair;
3. alert technique/event type is specifically consistent with Windows Security/Event Log clearing (for example T1070.001 / Windows Event Logs was cleared);
4. event timing is consistent with the exact Self-Heal job execution;
5. independent post-repair Quick Test is healthy;
6. there is no additional unexplained malicious process, persistence, credential, network, malware, or other suspicious security evidence associated with the alert/episode;
7. any generated Autotask side-effect ticket matches the same endpoint and correlated alert.

When all gates pass, Jason must:

1. identify and record the exact correlated EDR/SOC alert;
2. identify any Autotask ticket generated from that exact alert;
3. add an internal note stating that the alert/ticket was generated by the approved Security Log Self-Heal, including the primary remediation ticket and relevant job IDs;
4. resolve the exact correlated EDR/SOC alert;
5. verify the exact alert is no longer open or is resolved in authoritative alert history;
6. complete the exact correlated process-generated Autotask ticket after healthy endpoint verification;
7. verify that ticket status=Complete;
8. leave all unrelated alerts/tickets untouched.

If **any** correlation gate is uncertain or additional suspicious evidence exists, do not resolve the security alert automatically. Hand the primary/related work to Help Desk I / Human Review.

Ticket cleanup is a required autonomous completion step for an exactly correlated expected side effect, not optional housekeeping.

## 19. Final Resolution Note

Summarize:

- original Security Log failure
- diagnostic evidence
- approval/SOC-SIEM warning
- Self-Heal result
- independent healthy verification
- original alert disposition
- correlated EDR/SOC side-effect alert disposition
- process-generated Autotask ticket cleanup
- final timestamp/state

## 21. Acceptance Test

Controlled acceptance must prove:

- ticket creation/association and Jason ownership lifecycle
- online/offline handling
- Quick Test diagnosis
- one and only one autonomous Self-Heal attempt for the same incident state
- independent healthy verification
- original exact alert resolution with readback
- detection of expected `Windows Event Logs was cleared` side-effect
- exact endpoint/time/technique/job correlation of that side effect
- automatic resolution of only the exactly correlated side-effect alert
- automatic completion/readback of any exactly correlated process-generated ticket
- automatic completion/readback of the primary ticket
- ambiguous or extra security evidence routes to Help Desk I / Human Review
- no unrelated ticket/alert closure
- technician-scannable completion documentation

Validated production examples include SET-01 and CT100.
