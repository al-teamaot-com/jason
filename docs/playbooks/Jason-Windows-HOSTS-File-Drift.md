# Jason Playbook: Windows HOSTS File Drift

Version: 1.0.0  
Playbook ID: `windows_hosts_drift`  
Status: Governed playbook definition created from production evidence on 2026-09-22. Initial known-good patterns are evidence-gated; arbitrary HOSTS changes remain fail-closed.

## 1. Section Goal

**Goal:** Allow Jason to investigate Windows HOSTS-file drift alerts, distinguish approved/known-good changes from suspicious or unknown changes, document the evidence, and resolve only those alerts that meet explicit evidence-backed rules.

**Success means:**
- the exact ticket, client, endpoint, and DRMM alert are identified;
- added/removed HOSTS entries are captured exactly;
- known-good changes are recognized only when their rule and corroboration requirements match;
- unknown or security-relevant redirects are not silently accepted;
- Jason never treats an automatic baseline reset by itself as proof that a change is authorized;
- the DRMM alert and Autotask ticket are resolved only after authoritative verification and documentation.

## 2. Trigger

This playbook applies when:
- Autotask ticket or DRMM alert is generated by `Monitor HOSTS file Drift [WIN] AOT Ver 11262025-1`; or
- the alert context reports `Unhealthy - HOSTS drift detected`.

Jason must confirm the trigger is a Windows HOSTS drift event before starting.

## 3. Scope and Boundaries

### In Scope
- Autotask ticket/device correlation;
- DRMM endpoint and alert reads;
- exact added/removed HOSTS-line evidence;
- historical alert evidence for the same endpoint;
- DRMM software inventory and other local read-only evidence;
- known-good pattern classification;
- DRMM alert resolution;
- Autotask internal notes and ticket completion.

### Out of Scope
- arbitrary modification of `C:\Windows\System32\drivers\etc\hosts`;
- accepting an unknown change merely because a response component reset the baseline;
- accepting redirects for security, AV/EDR, identity, RMM, DNS-filtering, cloud, banking, or other sensitive services without explicit evidence;
- autonomous removal/addition of HOSTS entries outside a separately approved remediation;
- disruptive actions.

Preserve Central Orchestrator authority, `direct_provider_access=false`, exact requester grants, client isolation, audit logging, and existing approval rules.

## 4. Initial Identification

1. Resolve the exact Autotask ticket.
2. Resolve the client and configuration item.
3. Resolve the exact DRMM device UID.
4. Read the exact open DRMM alert.
5. Capture:
   - alert UID;
   - trigger time;
   - current HOSTS path;
   - current SHA256;
   - current file last-write time;
   - baseline SHA256;
   - lines added;
   - lines removed;
   - logged-on context;
   - response actions already performed.
6. Search endpoint alert history for prior HOSTS drift on the same device.

If identity is ambiguous: `state=identification_blocked`.

## 5. Expected State

Healthy state is one of:
- current HOSTS content matches the approved baseline; or
- the change exactly matches an approved known-good rule and corroborating evidence proves the rule applies to this endpoint/client.

A baseline reset is operational state, not authorization evidence.

## 6. State Model

Persist:
`identified -> diagnosing -> known_good_review -> verifying -> complete`

or:
`identified -> diagnosing -> unknown_change -> escalated`

Additional states:
- `identification_blocked`
- `awaiting_approval`
- `remediation_required`

## 7. Diagnostic Workflow

### Step 1: Capture exact drift
**Evidence source:** DRMM open alert diagnostics.  
**Expected result:** exact added and removed lines are available.

If the diagnostics are truncated or incomplete, do not classify the change as known-good.

### Step 2: Check same-endpoint history
**Evidence source:** `endpoint.alert.history.search`.  
Determine whether the exact line set, file SHA256, or file last-write timestamp has been seen previously on the same endpoint.

### Step 3: Gather corroborating endpoint evidence
Use the narrowest available reads, including:
- DRMM software inventory;
- historical component/cleanup evidence;
- prior approved ticket notes;
- documented client/site exception;
- known network-device/site configuration.

### Step 4: Apply known-good rules
A rule may be used only when its exact match requirements and corroboration requirements are satisfied.

## 8. Decision Gates

Before classifying a change as valid:
- endpoint identity must be exact;
- added/removed lines must be known;
- the change must match an approved rule exactly;
- required corroborating evidence must exist;
- there must be no additional unexplained lines in the same drift event;
- no evidence may indicate malicious redirection, compromise, or conflicting configuration.

If any gate fails, Jason must not auto-resolve the alert.

## 9. Remediation / Known-Good Handling

### Rule KG-HOSTS-001 — Adobe Creative Cloud WAM

**Exact valid block:**
```
## Adobe Creative Cloud WAM - Start ##
166.117.29.222 detect-ccd.creativecloud.adobe.com
## Adobe Creative Cloud WAM - End ##
```

**Classification:** known-good Adobe Creative Cloud WAM HOSTS change, but only when evidence-gated.

**Required match conditions:**
- exactly the three lines above are added as a block;
- no unrelated HOSTS entries are added or removed in the same drift event.

**Required corroboration — at least one strong same-endpoint source:**
- the identical block was previously observed on the same endpoint and previously accepted/closed;
- the same HOSTS SHA256 and file last-write timestamp prove the current alert is re-detecting an established file state;
- local endpoint evidence demonstrates Adobe/Creative Cloud presence or usage, such as software inventory, Adobe/CreativeCloud process/service evidence, or repeated Adobe/AdobeVulcan/CreativeCloud application data in prior governed diagnostics;
- a prior AOT-approved ticket or client-specific exception explicitly authorizes the block.

**Production acceptance evidence:**  
`T20260922.0009` / `DESKTOP-VQO1V44`:
- exact Adobe WAM block;
- same endpoint previously detected the identical block on 2026-03-27;
- current and historical alert evidence showed the same HOSTS SHA256 `1EE5FD84AFE5BD1551BD366314963A2F8396BEACD684673768C11E626A57D7CE`;
- same file last-write timestamp: 2026-03-27 07:03:10 local;
- historical DRMM cleanup evidence repeatedly referenced `Adobe`, `AdobeVulcan`, and `CreativeCloud` data for the same endpoint/user.

**Allowed action when all gates pass:**
- document the evidence;
- resolve the DRMM HOSTS alert;
- complete the Autotask ticket;
- do not modify the HOSTS file.

**Do not:** use the Adobe rule for different IPs/domains, partial matches, extra lines, or endpoints lacking corroboration.

### Rule KG-HOSTS-002 — Legacy AOT M-Central cleanup

Removal of the legacy AOT M-Central / `ncp.teamaom.com` HOSTS entry is expected and valid when:
- the endpoint/client has a documented AOT legacy-M-Central cleanup history or technician confirmation;
- no unrelated suspicious HOSTS changes are present.

Production evidence: `T20260922.0008` / `VSHF-DT-02`.

### Rule KG-HOSTS-003 — Approved client network-device mapping

A client-specific HOSTS mapping may be accepted when:
- the hostname/IP maps to a known network device or approved site connectivity design;
- the mapping is confirmed in prior ticket/documentation or by technician approval;
- the current file is intended to become the approved baseline;
- no unrelated suspicious changes are present.

Production evidence:
- `T20260922.0005` / `JBF-50406`: known network-device entry; technician confirmed the newly baselined HOSTS file is correct.
- `T20260922.0008` / `VSHF-DT-02`: approved `vdc-01` mappings associated with the client's ZeroTier path.

## 10. Retry Policy

- Maximum evidence-gathering attempts per provider read: 2 when a transient connector failure occurs.
- Do not repeatedly reset the HOSTS baseline.
- Do not retry an unknown change into an approved state.
- After bounded provider failures: document and escalate.

## 11. Periodic Rechecks

Normally not required after a known-good classification and verified DRMM alert resolution.

If the same exact approved block re-alerts:
- compare current SHA256, last-write timestamp, and exact line set;
- if unchanged and the prior approval evidence remains valid, treat as duplicate/stale-baseline recurrence;
- if any content differs, start a new investigation.

## 12. Aging / Stale Condition

Repeated alerts for an unchanged approved HOSTS file indicate monitor/baseline-state drift rather than a new endpoint change. Track recurring monitor behavior separately from the endpoint incident.

## 13. Dependency Handling

If classification depends on missing client/network documentation:
1. search existing Autotask/IT Glue evidence;
2. do not guess;
3. request technician/client confirmation where required;
4. keep the alert/ticket open or blocked until evidence exists.

## 14. Documentation Requirements

For every run document:
- ticket number;
- device;
- alert UID;
- current and baseline hashes when available;
- exact added/removed lines;
- historical match evidence;
- corroborating evidence;
- rule ID used, if any;
- whether a response component reset the baseline;
- final classification;
- alert-resolution result;
- ticket disposition.

Do not document secrets.

## 15. Failure Handling

If:
- alert diagnostics are incomplete;
- DRMM history is unavailable;
- device mapping is ambiguous;
- corroboration conflicts;
- the change affects sensitive security/cloud domains;
- a baseline was reset before the change could be independently classified;

then fail closed and escalate rather than declaring the change valid.

## 16. Escalation Criteria

Escalate when:
- no known-good rule matches;
- exact match exists but corroboration is missing;
- extra unexplained HOSTS lines are present;
- security/MSP/identity/DNS destinations are redirected unexpectedly;
- unauthorized file modification is suspected;
- remediation would require modifying the HOSTS file without pre-approved authority.

## 17. Verification

Known-good resolution requires:
- exact rule match;
- corroborating evidence;
- DRMM alert resolution readback;
- Autotask note documenting evidence;
- ticket status verified as Complete.

A successful baseline reset alone is not verification.

## 18. Completion Criteria

Complete only when:
1. identity is exact;
2. drift contents are known;
3. a known-good rule is proven or approved remediation has been completed;
4. no unexplained lines remain;
5. alert is resolved;
6. evidence is documented;
7. ticket completion is read back and verified.

## 19. Final Resolution Note

Include:
- original drift;
- exact added/removed lines;
- known-good rule ID;
- corroborating evidence;
- whether the file itself was modified;
- DRMM alert resolution;
- final ticket status.

## 20. Required Capabilities

Minimum capabilities:
- Autotask ticket read/search;
- Autotask internal note create;
- Autotask ticket update/readback;
- DRMM endpoint search/read;
- DRMM open-alert read;
- DRMM alert-history read;
- DRMM software inventory read when available;
- DRMM alert resolve;
- governed ad-hoc/component diagnostics only when separately approved;
- persisted playbook state.

## 21. Acceptance Test

**Production evidence target:** `T20260922.0009` / `DESKTOP-VQO1V44`.

Prove:
1. exact Adobe WAM block is captured;
2. March 27 same-endpoint historical alert is found;
3. SHA256 and last-write timestamp match;
4. Adobe/CreativeCloud local evidence is found in prior governed diagnostics;
5. rule `KG-HOSTS-001` is selected;
6. no HOSTS file modification occurs;
7. DRMM alert resolves;
8. Autotask evidence note is added;
9. ticket completion is read back.

This evidence was demonstrated on 2026-09-22.
