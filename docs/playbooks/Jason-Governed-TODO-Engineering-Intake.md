# Jason Playbook: Governed TODO Engineering Intake

## 1. Section Goal

Goal: Allow Jason to treat the governed Project Jason TODO backlog as an executable engineering intake source without allowing backlog ideas to bypass Support priority, development controls, Release Manager, protected-core approval, or production verification.

Success means:
- only actionable TODO statuses are admitted;
- Support List work retains higher priority;
- TODO work reuses the existing owner-approved development worker;
- a merged development PR is handed to Jason Release Manager by exact merge SHA;
- production deployment remains solely Release Manager responsibility;
- a TODO is marked Implemented only after Release Manager state is closed and production verification evidence exists.

## 2. Trigger

This playbook applies when the Project Jason TODO backlog contains an item whose status begins with Planned or In progress and no higher-priority Support scheduling condition prevents new TODO work.

Proposed, Researching, Blocked, Rejected, Implemented, Retired, and other non-actionable statuses are not automatic engineering triggers.

## 3. Scope and Boundaries

In scope:
- Project Jason TODO backlog;
- bounded GitHub engineering issues;
- existing owner-approved development worker;
- existing governed PR integration;
- Jason Release Manager;
- documentation-only TODO closure.

Out of scope:
- direct production deployment by the intake or bridge;
- provider authority changes;
- bypassing protected-core owner approval;
- implementing Proposed or Blocked ideas automatically;
- closing TODOs based only on a merge or deploy command.

Preserve direct_provider_access=false, Central Orchestrator authority, exact grants, provider/client isolation, approval requirements, disruption controls, and auditability.

## 4. Initial Identification

Jason must:
1. read the current TODO backlog from protected main;
2. parse the exact TODO ID, title, priority, status, and source section;
3. confirm status is actionable;
4. confirm no open engineering issue already binds that TODO ID;
5. evaluate current Support List state and active repair capacity;
6. confirm engineering capacity exists;
7. select the highest-priority eligible TODO deterministically.

## 5. Expected State

Healthy state means:
- every active TODO engineering item has one durable TODO ID;
- at most the configured number of TODO engineering issues are open;
- Support work is never displaced by lower-priority TODO admission;
- the shared development worker owns code implementation;
- Release Manager owns candidate, pre-production, promotion, verification, and rollback;
- the TODO backlog reflects Implemented only after authoritative production verification.

## 6. State Model

Intake states:

idle -> candidate_selected -> issue_created

Development states remain owned by the existing shared development worker.

Release-bridge states:

waiting_development_merge -> waiting_release -> closure_validating -> complete

Failure states:

release_prepare_blocked | release_blocked | closure_blocked

Waiting/release states do not imply production success.

## 7. Diagnostic Workflow

### Step 1: Parse actionable backlog

Purpose: determine which backlog entries are approved for autonomous engineering intake.

Evidence source: protected main TODO document.

Expected result: exact TODO ID with status Planned or In progress.

### Step 2: Support-first admission

Purpose: preserve known-defect priority.

Evidence source: SUPPORT.md plus persisted support-repair state.

Expected result: TODO start is allowed only when Support-first scheduling permits it.

### Step 3: Duplicate check

Purpose: avoid multiple engineering threads for one TODO.

Evidence source: open GitHub issues containing exact TODO item metadata.

Expected result: no existing issue for selected TODO.

### Step 4: Development handoff

Purpose: reuse common engineering behavior.

Evidence source: owner-approved development issue generated by intake.

Expected result: existing development worker accepts the bounded issue and performs normal search, edit, test, PR, and CI-repair workflow.

### Step 5: Release handoff

Purpose: keep deployment mechanics centralized.

Evidence source: merged development PR and exact merge SHA.

Expected result: TODO Release Bridge calls Release Manager prepare with the exact SHA and change class todo.

### Step 6: Production closure

Purpose: prevent merge/deploy from masquerading as completion.

Evidence source: Release Manager durable record.

Expected result: state closed with exact production live SHA and verification timestamp.

## 8. Decision Gates

Before issue creation:
- TODO status actionable;
- no duplicate issue;
- engineering capacity available;
- Support-first gate allows TODO work.

Before Release Manager handoff:
- owner-approved development PR carries `Integration automation: enabled`;
- protected integration checks are green and current-main reconciliation is complete;
- development PR merged through the governed source-integration path;
- exact 40-character merge SHA available.

Before TODO closure:
- Release Manager record exists for exact merge SHA;
- release state equals closed;
- production live SHA is exact;
- documentation closure PR records release evidence.

Protected-core Release Manager approval remains separate and cannot be granted by TODO intake.

## 9. Remediation

Not applicable in the operational-ticket sense.

Engineering implementation occurs through the existing owner-approved development worker. Production promotion occurs only through Release Manager.

Approval classification:
- backlog read: read-only;
- GitHub issue creation: modifying development metadata;
- source implementation: bounded development mutation;
- production deployment: Release Manager governed production action;
- protected-core production: exact owner approval required.

## 10. Retry Policy

- Do not create duplicate TODO issues.
- Release preparation is idempotent for an existing Production Eligible or later record.
- Failed, rolled-back, or blocked release records do not silently retry as successful.
- CI repair remains bounded by the shared development worker.
- Closure PR creation is idempotent by TODO closure metadata.

## 11. Periodic Rechecks

The engineering worker may re-run on its configured schedule.

Each run:
- reconciles Support priority;
- checks for eligible TODO intake;
- lets the shared development worker progress active work;
- automatically recycles bounded internal source-context/worker blockers while preserving real external/provider/authority blockers;
- records blocked development as blocked rather than mislabeling it as waiting for merge;
- reconciles merged TODO development with Release Manager;
- publishes an approved-commitment summary, including the invariant `release_queue_empty_but_upstream_pending`;
- checks for production-verified closure.

Unchanged waiting state does not create duplicate issues or closure PRs.

## 12. Aging / Stale Condition

A TODO candidate becomes stale when:
- its backlog status changes to non-actionable;
- the item is removed or replaced;
- dependencies become blocked;
- an existing development issue no longer matches the current TODO scope;
- Release Manager evidence no longer matches the exact merge SHA.

Stale work fails closed for human or Support review.

## 13. Dependency Handling

If implementation discovers a missing prerequisite or behavior Jason should already provide:
- do not hide the dependency inside TODO work;
- create/update the appropriate Support List item when it is a deficiency;
- allow Support-first priority to supersede normal TODO development;
- retain the TODO linkage so work can resume later.

## 14. Documentation Requirements

Persist:
- selected TODO ID;
- priority/status at admission;
- issue number;
- development PR number;
- exact merge SHA;
- Release Manager release ID/state;
- closure PR number;
- final production SHA.

Never store secrets in TODO state.

The TODO markdown itself is updated to Implemented only through a documentation PR after Release Manager closure.

## 15. Failure Handling

Failures must remain visible in persisted state.

Examples:
- no actionable TODO;
- Support-first admission denial;
- duplicate issue;
- GitHub issue creation/readback failure;
- owner-approved development blocked before PR creation;
- PR ready but not merged;
- merged PR without exact merge SHA;
- Release Manager unavailable;
- Release Manager failed/rolled back/blocked;
- closure PR failure.

A zero-length Release Manager queue is not completion evidence. If any owner-approved commitment remains upstream, status must expose it as outstanding and must not summarize the production pipeline as having nothing pending. No failure may be translated into Implemented.

## 16. Escalation Criteria

Escalate or block when:
- TODO scope is ambiguous;
- protected-core production approval is required;
- Release Manager is not healthy/available;
- release state is failed or rolled back;
- backlog and development issue materially disagree;
- closure evidence is contradictory.

## 17. Verification

The authoritative completion evidence is the Release Manager record, not source merge status.

Verification requires:
- release state closed;
- exact production live SHA;
- production verification timestamp;
- closure PR updates the exact TODO ID;
- original engineering issue is closed only after closure PR merge.

## 18. Completion Criteria

The TODO may complete only when:
1. exact TODO object was identified;
2. bounded development issue existed;
3. implementation PR merged;
4. exact merge SHA entered Release Manager;
5. isolated pre-production passed;
6. exact artifact was production verified;
7. Release Manager reached closed;
8. TODO markdown says Implemented with release evidence;
9. documentation closure PR merged;
10. engineering issue closed.

## 19. Final Resolution Note

The closure evidence must identify:
- TODO ID;
- development issue;
- implementation PR;
- Release Manager release ID;
- production SHA;
- production verification result/time;
- closure PR.

## 20. Required Capabilities

- protected repository TODO read;
- Support List read and persisted support state;
- GitHub issue read/create/close;
- existing owner-approved development worker;
- governed PR integration;
- Release Manager prepare/status/promotion lifecycle;
- persisted TODO intake/release state;
- documentation-only closure PR creation.

No new provider authority is granted.

## 21. Acceptance Test

Controlled source/non-production acceptance must prove:
1. Planned and In progress are eligible while Proposed is not;
2. Support-first scheduling blocks TODO admission when repair capacity exists;
3. duplicate TODO issues are suppressed;
4. generated issue carries exact TODO metadata and owner-approved development marker;
5. generated issue readback proves GitHub author_association=OWNER before the shared development worker is activated for TODO intake;
6. existing development worker remains unchanged;
7. merged issue/PR correlation yields exact merge SHA;
8. bridge invokes Release Manager prepare rather than deployment plumbing;
9. TODO closure rejects any release state other than closed;
10. closure changes only the targeted TODO section;
11. scheduler order is Support repair -> TODO intake -> development worker -> release bridge;
12. owner-approved development PRs opt into governed unattended source integration without a second owner phrase;
13. a blocked development worker is surfaced as `development_blocked`, not `waiting_development_merge`;
14. an empty release queue with upstream approved work sets `release_queue_empty_but_upstream_pending=true`;
15. bounded internal worker/context blockers can self-recycle while provider/authority/prerequisite blockers remain fail-closed.

Production activation is separate and must wait for the current Release Manager P0 acceptance path to be healthy.

## 22. Section Goal Closure

Close this implementation goal only after:
- protected CI passes;
- source integration is merged;
- host worker install is verified;
- dry-run shows Support-first behavior against the real backlog;
- one controlled actionable TODO is admitted only when policy permits;
- that item can be traced through development and Release Manager without bypasses.

## 23. Autonomous Execution Eligibility and Owner Review

The owner approved the TODO backlog as a normal engineering intake source on 2026-10-02.

That standing approval applies only to TODO items already marked Planned or In progress and does not grant:
- protected-core production approval;
- disruptive operational authority;
- provider permission expansion;
- authority to execute Proposed/Blocked ideas.

Protected-core production changes continue to require exact owner approval at the Release Manager gate.
